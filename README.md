# VisionLeaf AI

**Professional Digital Image Processing & Machine Learning Workbench**

A Streamlit application demonstrating a complete digital image processing
pipeline — from raw image acquisition through enhancement, restoration,
segmentation, morphology, ROI extraction, feature extraction, PCA, and SVM
classification — with built-in analytics and an experiment mode for
comparing restoration techniques quantitatively (PSNR / SSIM / MSE).

Built as a Digital Image Processing semester project, structured as a
production-quality, modular Python application.

> **Status:** Milestones 1–7 complete (Foundation, Application Shell,
> Image Management System, Core Digital Image Processing Engine, Image
> Processing Laboratory, Segmentation & ROI Engine, Feature Extraction
> Engine). See [`docs/MILESTONES.md`](docs/MILESTONES.md) for the full
> roadmap and what's implemented so far.

---

## Pipeline

```
Image Acquisition → Enhancement → Restoration → Segmentation
    → Morphological Operations → ROI Extraction → Feature Extraction
    → PCA → SVM Classification → Analytics → Experiment Mode
```

## Image Management System

Every image entering the pipeline flows through a centralized system
(built in Milestone 3) so all later stages — Enhancement, Segmentation,
Feature Extraction, Classification, and beyond — operate on one shared,
authoritative state instead of managing images independently:

- **`ImageSession`** (`visionleaf_ai/core/image_session.py`) — a plain
  dataclass holding the full lifecycle of one image: `original_image`,
  `current_image`, `grayscale_image`, `binary_image`,
  `segmented_image`, `roi_image`, `feature_vector`, `prediction`,
  `metadata`, and `processing_history`. Stored once, in
  `st.session_state["image_session"]`, via
  `visionleaf_ai/ui/session.py`'s `get_image_session()` /
  `set_image_session()`.
- **`ImageManager`** (`visionleaf_ai/processing/acquisition/image_manager.py`)
  — the only service allowed to load images: validates format/size,
  decodes, resizes if oversized, builds metadata, and records the
  initial history event. Later stages never load images themselves —
  they read `session.active_image`, write their own result field, and
  call `session.record_event(...)`.

The sample gallery (`assets/samples/`) ships with small, deterministic
**synthetic placeholder images** — clearly not real leaf photographs —
generated by `scripts/generate_sample_images.py`. Replace them with
real, appropriately-licensed leaf images before using this project for
actual disease classification (Milestones 7–8).

## Core Digital Image Processing Engine

Built in Milestone 4, and deliberately UI-free: no Streamlit code
lives under `visionleaf_ai/processing/`. Every algorithm is callable
(and unit-testable) with plain Python, independent of the app.

- **`PipelineStage`** (`processing/pipeline/stage.py`) — the abstract
  interface every algorithm implements: `process()`, `validate()`,
  `get_name()`, `get_description()`, `get_info()`. Because every
  algorithm shares this interface, they're fully interchangeable.
- **`PipelineEngine`** (`processing/pipeline/engine.py`) — the only
  way calling code (eventually, the UI) is meant to run an algorithm:
  `run_stage()` for one, `run_pipeline()` for a sequence (with
  cancellation — a failed stage stops everything after it),
  `run_by_name()` to run a registered algorithm by string name.
- **`AlgorithmRegistry`** (`processing/pipeline/registry.py`) —
  decorator-based (`@register_algorithm("name")`); adding an algorithm
  never requires touching an if/elif chain anywhere else.

```python
from visionleaf_ai.processing.pipeline import PipelineEngine

engine = PipelineEngine()
session, result = engine.run_by_name("gamma_correction", session, gamma=1.8)
print(result.success, result.duration_seconds)
```

**Available algorithms:**

| Category | Algorithm | Registry name |
|---|---|---|
| Enhancement | Brightness Adjustment | `brightness_adjustment` |
| Enhancement | Contrast Adjustment | `contrast_adjustment` |
| Enhancement | Gamma Correction | `gamma_correction` |
| Enhancement | Histogram Equalization | `histogram_equalization` |
| Enhancement | CLAHE | `clahe` |
| Restoration | Gaussian Blur | `gaussian_blur` |
| Restoration | Median Filter | `median_filter` |
| Restoration | Bilateral Filter | `bilateral_filter` |

Each algorithm's `get_info()` returns structured Purpose/Theory/Math/
Advantages/Limitations/Complexity documentation — this is what a
future Learning Mode panel will render, rather than hand-written UI copy.

## Segmentation & ROI Engine

Built in Milestone 6 as a pure extension of the same engine — no
redesign, same `PipelineStage`/`PipelineEngine`/`AlgorithmRegistry`
pattern, 22 more registered algorithms across three new stage
categories:

| Category | Algorithm | Registry name |
|---|---|---|
| Segmentation | Binary Threshold | `binary_threshold` |
| Segmentation | Binary Inverse Threshold | `binary_inverse_threshold` |
| Segmentation | Truncate Threshold | `truncate_threshold` |
| Segmentation | To Zero Threshold | `to_zero_threshold` |
| Segmentation | Otsu Threshold | `otsu_threshold` |
| Segmentation | Adaptive Mean Threshold | `adaptive_mean_threshold` |
| Segmentation | Adaptive Gaussian Threshold | `adaptive_gaussian_threshold` |
| Morphology | Erosion | `erosion` |
| Morphology | Dilation | `dilation` |
| Morphology | Opening | `opening` |
| Morphology | Closing | `closing` |
| Morphology | Morphological Gradient | `morphological_gradient` |
| Morphology | Top Hat | `top_hat` |
| Morphology | Black Hat | `black_hat` |
| ROI | Find Contours | `find_contours` |
| ROI | Contour Filtering by Area | `contour_area_filter` |
| ROI | Bounding Rectangle | `bounding_rectangle` |
| ROI | Minimum Area Rectangle | `min_area_rectangle` |
| ROI | Convex Hull | `convex_hull` |
| ROI | ROI Cropping | `roi_crop` |
| ROI | ROI Masking | `roi_mask` |
| ROI | Bounding Box Visualization | `bounding_box_visualization` |

**Two things worth knowing if you're extending this further:**

- **Masks chain like images do.** `ImageSession.active_mask` returns
  `segmentation_mask` if morphology has run, else `binary_image`, else
  `None` — directly parallel to `active_image`. Re-running a
  thresholding stage cascades through `clear_mask_results()`,
  invalidating any downstream mask/contours/bounding box/ROI images
  automatically.
- **Automatic ROI Extraction isn't a registered algorithm.** It's a
  plain function, `processing.roi.auto_extract.run_automatic_roi_extraction()`,
  that runs Otsu → Closing → Find Contours → Bounding Rectangle → ROI
  Cropping through the existing `PipelineEngine.run_pipeline()` —
  reusing five already-independent stages instead of duplicating them
  into one monolithic algorithm.

```python
from visionleaf_ai.processing.pipeline import get_pipeline_engine
from visionleaf_ai.processing.roi import run_automatic_roi_extraction

engine = get_pipeline_engine()
session, results = run_automatic_roi_extraction(engine, session)
print(session.roi_image.shape, session.bounding_box)
```

## Feature Extraction Engine

Built in Milestone 7 — the first stage in the pipeline whose output is
numbers, not images. Same pattern as every prior engine milestone: 6
more registered algorithms, no redesign.

| Category | Algorithm | Registry name |
|---|---|---|
| Color | Color Features (RGB/HSV mean, std, histograms) | `color_features` |
| Texture | GLCM Texture Features | `glcm_features` |
| Texture | Local Binary Pattern | `lbp_features` |
| Shape | Shape Features | `shape_features` |
| Edge | Edge Features | `edge_features` |
| Vector | Feature Vector Builder | `feature_vector_builder` |

```python
from visionleaf_ai.processing.pipeline import get_pipeline_engine

engine = get_pipeline_engine()
for name in ("color_features", "glcm_features", "lbp_features", "shape_features", "edge_features"):
    session, result = engine.run_by_name(name, session)

session, result = engine.run_by_name("feature_vector_builder", session)
print(session.feature_vector.shape)  # a fixed-length np.ndarray, normalized to [0, 1]
```

**Worth knowing if you're extending this further:**
- Every extractor requires `session.segmented_image` or
  `session.roi_image` to already exist — feature extraction never
  falls back to the raw uncropped photo, since "missing
  segmentation"/"missing ROI" are meant to be real, actionable
  validation errors, not silently-wrong statistics computed over
  mostly-background pixels.
- GLCM and LBP both write into the same `session.texture_features`
  dict, each under its own sub-key (`"glcm"`/`"lbp"`), so running
  either one never erases the other's results.
- `FeatureVectorBuilder` concatenates whichever groups have actually
  run, in a fixed documented order — building a dataset for Milestone
  8 means running the same extractors, with the same parameters, on
  every image, so every vector has the same length and meaning.

## Image Processing Laboratory

Built in Milestone 5 — the first real, user-facing page, and the
centerpiece of the application. Strictly UI → `PipelineEngine` →
`PipelineStage` → `ImageSession`: the page contains no pixel-
manipulation code of its own. Every "Apply" button does exactly one
thing:

```python
_, result = engine.run_by_name(selected_algorithm, session, **params)
```

**What it puts together:**
- **Interactive Comparison** — Side-by-Side and Before/After (a NumPy
  column-split composite) view modes, with zoom and fit-to-window
  controlled purely via `st.image(width=...)` — no resampling library
  is invoked for display, keeping the "never call OpenCV directly"
  boundary intact even for the viewer.
- **Enhancement Controls** / **Restoration Controls** — an algorithm
  picker sourced live from `AlgorithmRegistry.list_algorithms(category)`,
  with an **Algorithm Parameter Panel** showing only the sliders
  relevant to whichever algorithm is selected.
- **Histogram Viewer** (Plotly, per-channel) and **Pixel Statistics**
  (mean/std/min/max/dynamic range), both recomputed on every render —
  always current, never cached and stale.
- **Learning Mode** — when on, renders each algorithm's actual
  `AlgorithmInfo` (Purpose, Theory, Math Intuition, Advantages,
  Limitations) returned by its own `get_info()`, plus a plain-language
  explanation for each of its current parameters. The UI never
  maintains a second copy of this content.
- **Processing History**, **Image Metadata**, **Reset** (undo edits,
  keep the image), and **Export** (PNG/JPEG download) — all routed
  through `ImageSession`/`ImageManager`, never ad hoc in the page.

Because every stage chains onto `ImageSession.active_image`, Apply is
explicit rather than live-on-drag: dragging a slider only stages a
parameter value, so re-applying the *same* stage repeatedly (e.g.
while tuning Gamma) can't silently double-apply on top of itself.

## Configuration

All runtime behavior is controlled by [`config.yaml`](config.yaml) — no
hardcoded values in application code. Any setting can also be overridden
with an environment variable of the form `VISIONLEAF_SECTION__KEY`, e.g.:

```bash
export VISIONLEAF_APP__DEBUG=true
export VISIONLEAF_LOGGING__LEVEL=DEBUG
```
